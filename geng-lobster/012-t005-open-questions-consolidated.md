## Q1 · 并发上限（原 `010`）

- **背景**：`049` §三 冻结"并发上限 2 lane"。实测 CPU 均忙 **~64%（约 1/3 空闲）**，且瓶颈是**开销**（见 Q3），不是算力。
- **风险**：`T001` 的 stall 归因于并行/资源争用，我**无独立证据**证明加 lane 不复现；也看不到你分析侧对 wall-time 一致性的要求。
- **我的建议**：**维持 2 lane**。若你要提速，做**保守对照**：只加 1 条（总 3）、只跑**一个 seed 批次**、期间按进程树 CPU 判活统计 **stall 次数与 per-run 墙钟**，**恶化即回退 2 lane**，结果如实报你。
- **需要你给**：批准 / 否决 / 指定并发数与适用范围。

## Q2 · 每进程线程数（`011` §四-A）

- **实测**：两路并发时每进程 `num_threads=14`（intra 与 interop 均 14）→ **28 线程挤 14 核**（超额订阅）。微基准：**7 线程/进程 比 14 约 +8.0%**（1332→1438 ops/s，matmul 负载）。
- **性质**：属**改 harness**；且并行归约顺序可能带来 **1e-7 级数值差异**。
- **风险**：中途改 → **前 2 个 run 与后续不可比**。要改应**统一改在剩余全部 run**，或延到下一战役。
- **我的建议**：**延到下一战役**（当前战役的可比性优先于 8%）。
- **需要你给**：批准统一改剩余 run / 延后 / 否决。

## Q3 · DataLoader 工作进程（`011` §四-B）

- **实测**：30 秒内新建 **22 个 python 进程**（≈**0.73/秒**）—— Windows 上 `spawn` 反复起 DataLoader worker。我们的模型只有 2.8 万参数，**开销主导**，这一项很可能是**最大收益点**。
- **性质**：要改 `data_provider`（**harness 代码**）；`num_workers` / `persistent_workers` **不在冻结超参列表**内，但改了仍是改 harness。
- **我的建议**：同 Q2——**延到下一战役**；若你希望在**当前**战役生效，我建议**只对新开批次**统一启用并单独标注（牺牲小部分可比性换工期）。
