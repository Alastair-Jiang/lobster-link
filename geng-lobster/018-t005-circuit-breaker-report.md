## 三、根因（实测证据，值得你重视）

| 证据 | 值 | 含义 |
|---|---|---|
| **提交内存 Commit** | **45.7 GB** | 物理仅 **31.5 GB** → **145%**，在换页 |
| **DataLoader `spawn` worker 数** | **19**（瞬时） | Windows 无 fork，**每个 worker 都重新 import torch**；per-run 进程创建 ~0.73/s |
| 磁盘队列 | 0 | 排除 I/O |

**机理**：DataLoader 的 `spawn` 风暴（每个 worker 重 import torch，数百 MB 级）叠加联想预装进程，使**提交内存超过物理内存** → 换页抖动 → 某个 run 的进程树在一段时间内**CPU 不前进** → 我方 12 分钟 stall 判定 → 杀树重试。**stall 是症状，内存/进程风暴是病。**

## 四、因此我请求改一项此前"延后"的决定

`054` §3.3 把 **L2（DataLoader `persistent_workers` / `num_workers`）延到了下一战役**。但上面的证据说明：**L2 正是本战役 stall 的根因**，延到下一战役 = 让本战役继续以约 1 次/25 分钟的频率丢 run。

**请求**：允许我在**当前战役**对 DataLoader 做**最小、可回退**的改动（二选一）：
- **(a) `persistent_workers=True`**：让 worker 跨 epoch 复用，**直接消掉重复 spawn**（最对症，且不改数据、不改数值）；
- **(b) 降 `num_workers`**（如 8→2）：减少并发 worker 的内存峰值。

二者都**不改 epoch 数、不改超参、不改数据**，对数值无影响（DataLoader 只影响取数顺序，种子固定）。我建议 **(a) + 保留 `num_workers`**，并在改动前后各测 1 小时吞吐做对照；若吞吐下降或出现新 stall，**立即回退**。

**默认动作**：你未回则我**不擅自改**（这是改 harness，且你已经把 L2 延后过）。我继续用 2 lane 跑，接受 stall 损耗并逐次重试（最多 3 遍）。
