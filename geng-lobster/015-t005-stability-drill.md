## 二、B 的真实情况（重要，请记档）

**失败现象**（看门狗日志）：
```
15:02:30 lane0 missing but 4 run.py active -> defer
15:04:31 lane0 missing but 4 run.py active -> defer
15:07:56 lane0 missing -> restart (run.py active=4; lane will wait out duplicates)   <- 修复后
```
- lane0 被杀死后，看门狗**连续两轮推迟**，**没有任何 `lane0 missing -> restart` 行**；实测恢复耗时 **174 s 且并非看门狗所为**（是后续人工/其他动作）。
- **根因**：守卫写成 `if (run.py 全局计数 >= 2) { defer }`。双 lane 常驻 4 个 run.py 进程 → 条件恒真 → **死掉的 lane 永不恢复**。
- **修复**：**删除该门槛**，改为无条件重启。安全性由 lane 自身承担 —— 我在 lane 脚本里已有 `Test-TaskRunning`：重启后的 lane 若发现同一 run 仍在飞，会 `WAIT` 而不是重复起跑（14:58/15:07 两次日志均为 `WAIT(duplicate in flight)`，已实证）。同时把看门狗轮询 **120 s → 30 s**。
- **复验**：杀掉 lane0 → **29.1 s** 被拉起，日志出现 `lane0 missing -> restart (run.py active=4; lane will wait out duplicates)` → **PASS**。

## 三、两条测量教训（我自己的错，也记档）

1. **计数自匹配**：在"命令行里含 `t005_lane.ps1` 字样"的进程内做计数，会把**执行者自己**算进去 → 第一轮演练里"0.9 s 重启""杀掉后仍有 2 个检查点"全是**假阳性**。**改法**：测量代码放进**独立脚本文件**（文件名不含被搜字符串），或显式排除执行者 PID。
2. **按名字模式去重会误杀**：我用"按命令行模式删重复实例"清理，结果**杀掉了一个存活中的看门狗**（因为调用者的命令行同样含该模式）。**已把该脚本改成只报告、绝不自动杀**。教训：**按名字/模式批量 kill 是危险操作**，尤其在自指场景。

## 四、环境事实（解释 process 计数，避免你误判）

本机 `.venv\Scripts\python.exe` 是**启动器桩**：每次调用呈现 **父(桩)+子(真解释器)** 一对进程。因此：
- `run.py` 显示 4 个进程 = **2 个 run**；
- `checkpoint` 显示 2 个进程 = **1 个检查点**。
交接单/manifest 里的 run 数不受影响，但**看进程数时请按一半读**。
